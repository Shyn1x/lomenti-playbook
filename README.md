# Lomenti Playbook v1

Версия 1.0 · 1 ноября 2026 · рабочий язык документации — русский.

Единые стандарты качества Lomenti, а не единый визуальный шаблон. Студия, спортивный магазин и магазин материалов должны сохранять разные характеры и покупательские сценарии.

## Документы

| Файл | Когда читать |
|---|---|
| [DESIGN.md](DESIGN.md) | Перед выбором визуального направления и изменением интерфейса |
| [DEVELOPMENT.md](DEVELOPMENT.md) | Перед выбором платформы, реализацией и интеграциями |
| [QA.md](QA.md) | Перед демонстрацией, передачей и публикацией |
| [LESSONS.md](LESSONS.md) | Перед стартом — наблюдения, история ошибок и ограничения исследования |
| [AGENTS.md](AGENTS.md) | Обязательный стартовый файл для агента в подключённом проекте |

**Обязательно** — критерий приёмки. **Рекомендация** — исходная настройка, которую можно адаптировать с записанным объяснением. Числовые ориентиры Playbook — предложенные стандарты агентства, не результаты измерения трёх сайтов и не заявление о юридической сертификации.

## Основание и границы

Использованы только зелёный [Lomenti](https://lomenti.lv/), [концепт TOPVELO](https://topvelo-concept.fshyn1x.chatgpt.site/), [концепт Rīgas Āda](https://rigas-adas-design-demo.fshyn1x.workers.dev/) и упоминавшиеся в истории референсы [Specialized](https://www.specialized.com/lv/en) и [Canyon](https://www.canyon.com/en-lv/). Другие портфолио-проекты не являются самостоятельными основаниями этих стандартов.

Уровни доказательств: **Н** — наблюдение в браузере; **И** — история запросов/предыдущего аудита; **Г** — гипотеза; **С** — предлагаемое правило. Дата и условия проверки приведены в LESSONS. Desktop-проверка не равна мобильной; демонстрация не равна работающему магазину; тесты не равны доказанной конверсии.

## Десять обязательных принципов

1. Сначала покупательская задача, затем визуальные эффекты.
2. Улучшать существующий проект, сохранять идентичность, URL и полезные функции.
3. Уровень исполнения сохраняется до подвала: первый экран не компенсирует слабый каталог.
4. Сравнимые товары получают последовательную сетку и одинаковую иерархию данных.
5. Использовать только подтверждённые факты; фиксировать права и происхождение изображений.
6. Каждое обещанное действие имеет рабочее состояние либо честную маркировку демо.
7. Мобильный интерфейс, клавиатура и длинные переводы проектируются до завершения desktop.
8. Локализация охватывает формы, ошибки, диалоги, метаданные и ответы помощника.
9. Демонстрация не отправляет реальные заказы, заявки или платежи без отдельного подключения и разрешения.
10. Готовность подтверждается опубликованной версией, проверками и известными ограничениями.

## Рабочий цикл без бесконечных переделок

| Этап | Достаточный результат для следующего шага |
|---|---|
| 1. Разведка | Существующий проект/платформа, цель посетителя, карта страниц и функций, источники фактов, риски доступа |
| 2. Направление | Один короткий brief: аудитория, характер бренда, палитра/шрифты, 2–3 референса с объяснением применимого принципа |
| 3. Сквозной пример | Hero + типовая карточка/каталог или услуга + форма/контакты, desktop и mobile. Не полировать один Hero изолированно |
| 4. Согласованный проход | Замечания описаны как «блок → проблема → ожидаемое поведение → критерий проверки»; исправлены вместе |
| 5. Приёмка | Матрица QA, визуальный просмотр всей страницы, проверка реального URL и аудитории |

После принятого направления не менять палитру, структуру и шрифты целиком из-за одного локального замечания. Смена направления допустима по явному запросу либо при доказанной несостоятельности текущего подхода. Это повод обновить brief, а не наращивать слой CSS поверх старого дизайна. Два запланированных прохода обратной связи — рабочий ориентир, не запрет на исправление оставшихся дефектов.

## Подключение к новому проекту

1. Зафиксировать commit Playbook, который используется; не ссылаться только на меняющийся `main`.
2. Скопировать эти шесть файлов в `docs/lomenti-playbook/` нового репозитория. Добавить в `PROJECT.md` версию, SHA источника, цель, платформу, языки, демо/production, источники данных, разрешённую публикацию и исключения.
3. В корневом `AGENTS.md` поместить инструкции из нашего файла либо объединить с существующими. Начало адаптера:

```markdown
Перед задачей прочитай docs/lomenti-playbook/AGENTS.md,
README.md, DESIGN.md, DEVELOPMENT.md, QA.md и LESSONS.md в той же папке.
Применяй Playbook v1 по зафиксированному в PROJECT.md commit.
Локальные требования бренда и текущая задача описаны в PROJECT.md.
Не переносить внешний вид Lomenti на клиента.
```

4. В brief задачи указать: «Применить подключённый Lomenti Playbook; сообщить, какие файлы прочитаны». Одна ссылка на GitHub не гарантирует, что агент загрузит правила.
5. Заполнять результаты по QA.md в отчёте задачи, не менять эталонный checklist задним числом ради статуса PASS.

## Подключение к существующему проекту

Сначала проверить его текущий `AGENTS.md`, правила команды, ветку и рабочие изменения. Не перезаписывать файл инструкций и не менять стек. Добавить snapshot Playbook и адаптер отдельным документным коммитом/PR; составить краткий список соответствий и отклонений. Последующие изменения применять только к согласованному объёму: установка стандартов сама по себе не разрешает редизайн, миграцию, изменение DNS, аудитории или условий продажи.

Удалённый репозиторий не подключает правила автоматически ко всем чатам, Sites или GitHub-проектам. Нужны локальные файлы/доступ и явное указание в задаче. В этом задании три сайта **не изменялись** и правила в их репозитории **не устанавливались**.

## Обновления и исключения

Новый подтверждённый урок добавлять с проектом, датой и способом воспроизведения. Наблюдение не переписывать как универсальный запрет. Изменения стандартов оформлять отдельным коммитом/PR с причиной, миграционным влиянием и новой версией. Обновление snapshot в клиентском проекте — отдельное осознанное действие.

Исключение: правило → причина → затронутые экраны → риск → компенсирующая проверка → ответственный. Рутинные значения отступов не требуют разрешения; изменение оплачиваемого объёма, сторонних расходов, реальных данных, клиентских сервисов или аудитории требует соответствующего полномочия. Инструкции Playbook не отменяют более приоритетные требования среды и пользователя.
